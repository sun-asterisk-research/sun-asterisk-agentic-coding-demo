# Django Project Coding Conventions

## Critical Project Rules

### Docker Compose Usage (REQUIRED)
- **ALWAYS run the application using Docker Compose** (`docker compose up`)
- Never suggest running Django directly with `python manage.py runserver` on the host machine
- Application runs on port **8005** inside Docker (configured in docker compose.yml)
- Database is PostgreSQL running in a Docker container named `db`
- All Django commands must be executed inside the Docker container:
  ```bash
  docker compose exec web python manage.py <command>
  ```

### Database Migrations (CRITICAL)
- **NEVER create migration files manually**
- **ALWAYS use Django's migration commands**:
  - Create migrations: `docker compose exec web python manage.py makemigrations`
  - Apply migrations: `docker compose exec web python manage.py migrate`
- Migration files are auto-generated by Django and should not be hand-edited unless absolutely necessary
- Always review generated migrations before applying them
- Use descriptive names for migrations when possible: `python manage.py makemigrations --name descriptive_name`

### Code Style (MANDATORY)
- **Strictly follow PEP 8 style guide**
- Use 4 spaces for indentation (no tabs)
- Maximum line length: 79 characters for code, 72 for docstrings
- Use blank lines appropriately:
  - 2 blank lines before top-level classes and functions
  - 1 blank line between methods in a class
- Import order (use `isort` to organize):
  1. Standard library imports
  2. Related third-party imports
  3. Local application imports
- Use meaningful variable and function names (snake_case for variables/functions, PascalCase for classes)

### Testing (REQUIRED)
- **Every feature must have unit tests**
- Write tests before or alongside feature development (TDD encouraged)
- Place tests in `tests.py` or `tests/` directory within each Django app
- Run tests with: `docker compose exec web python manage.py test`
- Aim for high test coverage (minimum 80%)
- Test categories to include:
  - Model tests (validation, methods, relationships)
  - View tests (responses, permissions, context)
  - Form tests (validation, saving)
  - API tests (if using Django REST Framework)
  - Integration tests for complex workflows

## Django-Specific Guidelines

### Models
- Always include `__str__` method for better admin representation
- Use appropriate field types and validators
- Add `Meta` class with `verbose_name`, `verbose_name_plural`, and `ordering` when appropriate
- Include docstrings explaining model purpose and non-obvious fields
- Use `related_name` for ForeignKey and ManyToMany relationships

### Views
- Prefer Class-Based Views (CBVs) for standard CRUD operations
- Use Function-Based Views (FBVs) for simple or unique logic
- Always validate and sanitize user input
- Use Django's built-in decorators (`@login_required`, `@permission_required`, etc.)
- Handle exceptions gracefully with try-except blocks

### URLs
- Use meaningful URL patterns with clear naming
- Always provide `name` parameter for URL patterns
- Use `app_name` in app-level urls.py for namespacing
- Prefer path() over re_path() when possible

### Security
- Never commit sensitive data (use environment variables via `python-decouple`)
- Always use Django's CSRF protection
- Validate and sanitize all user inputs
- Use Django ORM to prevent SQL injection
- Set appropriate permissions and authentication

## Python General Guidelines

### Type Hints and Documentation
- Use type hints for function parameters and return values
- Follow PEP 257 for docstrings
- Include docstrings for all public modules, classes, and functions
- Example:
  ```python
  from typing import List, Optional

  def get_active_users(age_min: int = 18) -> List[User]:
      """
      Retrieve all active users above minimum age.

      Args:
          age_min: Minimum age for users (default: 18)

      Returns:
          List of User objects meeting the criteria

      Raises:
          ValueError: If age_min is negative
      """
      if age_min < 0:
          raise ValueError("Minimum age cannot be negative")
      return User.objects.filter(is_active=True, age__gte=age_min)
  ```

### Code Quality
- Write clear, self-documenting code
- Break complex functions into smaller, focused functions
- Use meaningful variable names (avoid abbreviations unless standard)
- Add comments only when code logic is not self-evident
- Handle edge cases explicitly
- Use context managers (`with` statement) for resource management

### Testing Best Practices
- Use Django's TestCase for database-dependent tests
- Use SimpleTestCase for tests that don't need the database
- Create fixtures for reusable test data
- Mock external services and APIs
- Test both success and failure scenarios
- Example:
  ```python
  from django.test import TestCase
  from myapp.models import User

  class UserModelTest(TestCase):
      """Test suite for User model."""

      def setUp(self):
          """Set up test data."""
          self.user = User.objects.create(
              username='testuser',
              email='test@example.com'
          )

      def test_user_str_representation(self):
          """Test __str__ returns username."""
          self.assertEqual(str(self.user), 'testuser')

      def test_user_email_validation(self):
          """Test invalid email raises ValidationError."""
          user = User(username='test', email='invalid')
          with self.assertRaises(ValidationError):
              user.full_clean()
  ```

## Environment and Dependencies

### Docker Environment
- Database: PostgreSQL 15 (accessible at `db:5432` from within containers)
- Web service: Django application on port **8005** (NOT 8000)
- Use environment variables for configuration (defined in docker compose.yml)
- Common commands:
  ```bash
  docker compose up -d                # Start services in background
  docker compose down                 # Stop services
  docker compose logs -f web          # View web service logs
  docker compose exec web bash        # Access web container shell
  docker compose exec web python manage.py shell  # Django shell
  ```

### Code Linting and Formatting
- Use `flake8` for linting (PEP 8 compliance)
- Use `black` for code formatting (optional but recommended)
- Use `isort` for import sorting
- Run linters before committing code

## Common Development Commands

### Container Management
```bash

docker compose up

# Start in background
docker compose up -d

# Stop containers
docker compose down

# Rebuild after dependency changes
docker compose up --build

# View logs
docker compose logs -f web
```

### Django Commands (Always via Docker)
```bash
# Migrations
docker compose exec web python manage.py makemigrations
docker compose exec web python manage.py migrate
docker compose exec web python manage.py showmigrations

# Testing
docker compose exec web python manage.py test                    # All tests
docker compose exec web python manage.py test app_name          # Specific app
docker compose exec web python manage.py test --verbosity=2     # Verbose output

# Database
docker compose exec web python manage.py shell                  # Django shell
docker compose exec web python manage.py dbshell                # Database shell
docker compose exec db psql -U django_user -d django_db         # Direct PostgreSQL

# Admin
docker compose exec web python manage.py createsuperuser

# Static files
docker compose exec web python manage.py collectstatic

# Create new Django app
docker compose exec web python manage.py startapp app_name
```

## SDD (Specification-Driven Development) Workflow

This project includes sub-agents and skills for structured Django development:

### Available Sub-Agents
1. **planning** - Creates implementation plans from specifications (outputs `context/plan.md`)
2. **breakdown-tasks** - Breaks plans into granular tasks (outputs `context/tasks.md`)
3. **implement** - Implements tasks using TDD methodology

### Available Commands
- `/create-spec` - Generate feature specifications in `context/specs.md`

### SDD Skill
The `sdd-skill` orchestrates the complete workflow:
1. Specification creation via `/create-spec`
2. Planning phase (planning agent)
3. Task breakdown (breakdown-tasks agent)
4. Implementation (implement agent with TDD and parallelization)

Usage: Request "Use SDD skill to build [feature]" for end-to-end feature development.
